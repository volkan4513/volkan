How it works · Project 08

Low-Poly Strike

A 4v4 first-person shooter that runs in the browser. One player hosts, everyone else connects peer to peer.

What it is

A low-poly shooter in the style of Counter-Strike 1.x. Play solo against bots (Free Area), or host a match for friends. Up to 4 humans per team, bots fill empty seats. Works with keyboard and mouse or on a phone in landscape.

Everything is plain JavaScript and Three.js. The whole game, including the multiplayer code, is shipped as static files, so it runs on GitHub Pages.

How it loads

  • Plain ES modules from local files, no bundler, no CDN. game.js is a module and fetches the three map files and weapons.json in parallel at start.
  • PeerJS is loaded on demand the first time you host or join.
  • The Dust II 3D model is fetched only when that map is used. A small hand-written GLB reader (parseGlb in game.js) draws it, while the invisible collision boxes from map3.json do the actual collision.
  • offline.js registers the service worker, so a friend who opens a shared game link also gets the offline cache. Free Area works offline.
  • Settings are saved in localStorage under lp-strike-settings.

How multiplayer works here

Both games use PeerJS (a small helper around WebRTC) to connect players straight to each other. There is no game server of our own.

Joining by room code

  1. The host taps Host. The game makes a random 5-character code (letters and digits without I, L, O, 0 and 1, so it is easy to read out loud) and registers it with the free PeerJS cloud under an id such as lpstrike-K7QM2 (08) or pxracer-K7QM2 (09).
  2. A friend types the code (or scans the QR code, see below). Their browser asks PeerJS for that id. PeerJS only passes the connection details (the "signalling" step) and then steps out of the way.
  3. The two browsers now talk directly over WebRTC data channels. If a direct path is impossible (strict network), PeerJS cloud also offers a relay (TURN) as a fallback.
  4. The friend sends hello with their name. The host must receive it within 5 seconds or the link is dropped.

Two channels per player

ChannelTypeCarries
relOrdered and reliablehello, welcome, lobby, roster, start, map choice, buy, team, heartbeat, bye
fastUnordered, no resends (maxRetransmits: 0)Inputs and snapshots (08), car states (09). A late packet is useless, so it is never re-sent.

The joiner opens fast once rel is up. If fast never opens, everything falls back to rel: slower, but it still works.

Health checks

  • A heartbeat every 2 seconds. A link with no data for 6 seconds is closed. The round-trip time (ping) is smoothed and shown.
  • Joiner loses the host: "Lost connection to the host" and back to the menu. Host leaves: everybody is told "The host closed the game". There is no host migration.
  • The PeerJS library is loaded only when someone hosts or joins (a local copy, no CDN).

QR code and links

  • The host lobby shows a QR code that contains a link like .../projects/08/index.html?join=K7QM2.
  • Scanning it with any phone camera opens the game with the code filled in, and it joins automatically.
  • The join screen also has a Scan QR code button that reads the code with the camera. It only appears in browsers that support BarcodeDetector (Android Chrome, macOS). On iPhone and Windows Chrome use the camera app or type the code.
  • The QR link uses the address the page was opened from, so open the game from the real website (not localhost) when hosting for friends.
  • Files: qrcode.js draws the code, joinqr.js has draw, scan and codeFrom.

Test knobs (URL)

  • ?lag=120 delays everything this tab sends by 120 ms. ?loss=5 drops 5% of the fast packets. Browser DevTools throttling does not touch WebRTC, so use these to test bad connections.

Who is in charge (host-authoritative)

  • The host's browser runs the real simulation (stepWorld in sim.js, 60 times a second): movement, shots, damage, rounds, the bomb and the bots. Clients only send what they pressed.
  • Client to host: inputs about 30 times a second. The last 12 unconfirmed inputs ride in every packet, so a lost packet costs nothing.
  • Host to client: a snapshot 20 times a second with every player's position, health and state, plus a private block for that player (confirmed input number, exact position, ammo, money).

Making it feel instant

  • Prediction: your own player moves immediately on your screen. When a snapshot arrives, your state is overwritten with the host's, the inputs the host already used are dropped, and the rest are replayed on top. If you and the host agree nothing visibly changes.
  • Interpolation: other players are drawn 100 ms in the past, smoothly between two snapshots. A jump of more than 6 metres (a respawn) snaps instead of sliding.
  • Lag compensation: every shot carries the host tick the shooter was looking at. The host keeps 0.5 seconds of player positions, moves everyone back to that moment, fires the ray, and puts them back. A shot that looked like a hit on your screen counts as a hit. The side effect: a laggy shooter can hit someone who has already reached cover on the host.
  • Input queue: the host plays one client input per tick like a jitter buffer. Bursts are played out, short gaps repeat the last input, a long gap stops movement and fire, and a held Use is remembered for up to 1 second so planting does not reset.

When someone drops

  • If Fill with bots is on, the missing player's seat becomes a bot. Otherwise they are removed.
  • A player who joins a running match takes a bot's seat when their team is full.
  • The screen is kept awake (Wake Lock) during an online match.

Game logic

  • Physics (sim.js): fixed 1/60 s step, run 6.2 m/s, walk 3.0, crouch 2.4, jump 7.6, gravity 20, step-up 0.5 m. Collision is axis by axis against boxes using a grid for speed.
  • Shots: hitscan rays against player boxes (a head box gives the headshot multiplier) and against map boxes, so walls block.
  • Weapons: pistol, rifle (automatic), shotgun (9 pellets), sniper (90 damage, 4x scope). All numbers live in weapons.json.
  • Bots: a waypoint graph is built from the map (explicit links on Dust II, automatic links within 24 m elsewhere). Bots use A* paths, line-of-sight checks, a reaction delay and aim error that depend on Easy, Normal or Hard. They produce the same input as a human, so the same simulation runs them. In bomb mode they plant, guard and defuse, and buy weapons.
  • Maps: boxes drawn procedurally with textures, or a GLB model for visuals with the boxes kept invisible for collision.

Making or changing a map

Simple maps (Yard, Dust) are just JSON: boxes, spawn points, bomb sites and waypoints. Copy a map*.json, edit it and add the file name to the map list in game.js.

Dust II is generated: node projects/08/tools/build_dust2.mjs reads the 3D model, scales it to metres, turns it into small voxels, merges them into collision boxes, and floods outward from the spawns to find walkable waypoints. dust2_meta.mjs holds the hand-placed data (spawns, bomb sites, credit). Credits for the model are in extra_map/CREDITS.txt.

How it differs from the other projects

  • The only project with authoritative server logic (running inside the host's browser), client prediction and lag compensation.
  • Compared with Pixel Racer (09), which uses the same connection code: there every player drives their own car and the host just relays, with no prediction.
  • Has Node tooling for map generation; the racer's tracks are hand-built data.

Main quality

A complete multiplayer shooter with no backend of our own: host-authoritative rules, prediction and lag compensation, three modes, bots and touch controls, all in about a megabyte of code.
